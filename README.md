# kb-rag-assistant

Небольшой RAG-помощник по базе знаний продукта: находит релевантные фрагменты
документации в ответ на вопрос пользователя и формирует ответ. Есть CLI и
веб-интерфейс. Сделан как демо-проект, приближённый к реальной задаче
поддержки SaaS/POS-продукта — например, чтобы отвечать на типовые обращения
клиентов автоматически или подсказывать оператору поддержки готовый ответ
со ссылкой на источник.

## Быстрый старт

```bash
pip install -r requirements.txt

# Построить индекс из data/docs
python -m app.ingest

# Вариант 1: консольный чат
python -m app.cli

# Вариант 2: веб-интерфейс
uvicorn app.web:app --reload
# затем открыть http://127.0.0.1:8000
```

Пример вопроса: `что делать если платёж не прошёл`

## Два бэкенда ретривера

Выбираются переменной окружения `RETRIEVER_BACKEND`:

| Бэкенд | Как работает | Плюсы | Минусы |
|---|---|---|---|
| `tfidf` (по умолчанию) | TF-IDF + косинусная близость | Работает офлайн, ничего не качает, детерминирован | Ищет по совпадению слов, не по смыслу |
| `embeddings` | Семантический поиск (sentence-transformers, многоязычная модель) | Понимает смысл вопроса, а не только слова | При первом запуске качает модель (~470 МБ) с huggingface.co, дальше работает из локального кэша |

Переключение:

```bash
# Linux/macOS
export RETRIEVER_BACKEND=embeddings
python -m app.ingest
python -m app.cli

# Windows cmd
set RETRIEVER_BACKEND=embeddings
python -m app.ingest
python -m app.cli
```

Оба бэкенда реализуют один и тот же интерфейс (`build/save/load/search`) —
остальной код (`rag.py`, `cli.py`, `web.py`) от выбора бэкенда не зависит,
переключение ничего в них не меняет.

## Генерация ответа: generative / extractive

- Если задан `OPENAI_API_KEY` — найденные фрагменты передаются модели как
  контекст, и она формулирует связный ответ (классический RAG).
- Если ключа нет — движок возвращает сам найденный фрагмент как есть
  (extractive-режим). Так демо работает из коробки у любого, кто
  склонирует репозиторий, без необходимости платить за API.

Чтобы включить генеративный режим: скопируй `.env.example` в `.env`, впиши
`OPENAI_API_KEY`, экспортируй переменную окружения перед запуском.

## Структура

```
app/
  chunking.py              # разбивка markdown-документов на чанки по заголовкам
  index_store.py             # TF-IDF бэкенд + фабрика build_index/load_index
  embeddings_retriever.py    # семантический бэкенд (sentence-transformers)
  rag.py                       # поиск + генерация ответа (generative / extractive)
  ingest.py                    # CLI: строит индекс из data/docs
  cli.py                        # CLI: интерактивный чат с базой знаний
  web.py                        # FastAPI: веб-интерфейс
  templates/index.html          # HTML-шаблон веб-интерфейса
data/docs/                     # 6 markdown-документов условной базы знаний POS/SaaS-продукта
tests/test_retrieval.py       # проверка, что по вопросу находится правильный документ
```

## Тесты

```bash
pytest
```

Тесты покрывают TF-IDF бэкенд (работает офлайн, без скачивания моделей) и
проверяют, что по типовым вопросам ретривер находит именно ожидаемый
документ, а на нерелевантный запрос не возвращает уверенных совпадений.

## Возможные развития проекта

- Векторная БД (Chroma/Qdrant) вместо pickle-файла — чтобы не пересобирать
  индекс с нуля при каждом добавлении документа.
- Логирование вопросов, на которые не нашлось хорошего ответа — сигнал,
  какие темы нужно добавить в базу знаний (реальная задача из вакансий
  поддержки: "анализировать повторяющиеся обращения и искать их первопричины").
- Ранжирование ответа с учётом нескольких найденных источников, а не только
  самого релевантного.
- Эскалация к живому оператору, если релевантность найденного ниже порога.
